# L04 Reproducible rover bringup

Самостоятельная домашняя работа после практики. Цель — подключить inspection rover к ROS и доказать корректность измерений и повторного запуска. Ориентир по нагрузке — 2–3 часа; скорость первого скачивания образа сюда не входит.

## Задача

Сцена, физическая модель, Docker, launch и сбор сообщений предоставлены. У inspection rover другие Gazebo endpoints, чем у практического примера. Завершите соединение пяти прикладных каналов, настройте sensor systems и реализуйте анализ измерений, который корректно обрабатывает reset времени.

Изменяйте три файла:

| Файл | Самостоятельная часть |
|---|---|
| `homework/wiring.yaml` | ROS names, ROS/Gazebo types и direction пяти каналов |
| `homework/systems.yaml` | Sensor systems и частоты |
| `src/rover_sim_lab/rover_sim_lab/homework_metrics.py` | Функция `analyze_samples(records)` |

Дополнительно добавьте собственный тест и `docs/diagnosis.yaml`, сохраните evidence. При оценивании запускается выданная инфраструктура с вашими тремя файлами; изменения служебного launch, observer, checker или практической конфигурации не заменяют решение. Весь программный интерфейс описан в [контракте](CONTRACT.md).

## A Соединение интерфейсов

В `wiring.yaml` сохраните ключи каналов и фиксированные Gazebo suffixes. Заполните TODO для `command`, `scan`, `imu`, `image`, `info` по контракту. Выберите явное направление каждого соединения. Имена ROS задавайте относительно namespace, без жёстко записанного `/rover`.

Clock, odometry, joints, odom TF и канал проверяющего наблюдения уже подключены. Собственный источник `/clock` или параллельный publisher того же TF добавлять не нужно. Image и CameraInfo должны сохранять optical frame и согласованные параметры камеры.

## B Сенсоры

В `systems.yaml` укажите необходимые sensor systems и задайте scan 10 Hz, IMU 100 Hz, camera 10 Hz. Odometry 50 Hz и камера 160 × 120 предоставлены. Исправлять физическую модель и переносить модель из L03 не требуется.

После правки конфигурации:

```bash
./course build
./course homework
```

Проверьте визуально и через topic inspection команду скорости, движение, scan, IMU, Image и CameraInfo. Незавершённый starter должен давать диагностику TODO; успешная сборка ещё не означает рабочий запуск.

## C Анализ временного ряда

Вход функции — список записей в порядке поступления. Каждая запись содержит:

- `stamp`: время измерения в секундах simulated time;
- `arrival`: время получения по monotonic clock в секундах;
- `value`: gyro z в rad/s либо `None` для других потоков.

В рамках этого задания stamps и arrival конечны, arrival не убывает. Любое уменьшение stamp начинает новую эпоху. Вычисляйте метрики только по последней эпохе. Одинаковые stamps внутри эпохи учитывайте один раз, сохраняя первое получение. Входной список не изменяйте.

Верните словарь с ключами:

| Ключ | Значение |
|---|---|
| `samples` | Число уникальных samples последней эпохи |
| `epochs` | Число эпох во всём входе; 0 для пустого списка |
| `sim_hz` | Частота по stamps последней эпохи |
| `wall_hz` | Частота по arrival соответствующих samples |
| `gyro_mean` | Среднее конечных `value` последней эпохи |
| `gyro_std` | Population standard deviation конечных `value`, `ddof=0` |

Для частоты нужны минимум два уникальных sample и положительный интервал соответствующих часов; иначе возвращайте `None`. Если конечных gyro values нет, обе gyro-метрики равны `None`; при единственном конечном значении std равна 0. `NaN`/`inf` в `value` пропускайте. Нулевой stamp допустим: это может быть начало симуляции.

Формулы из лекции можно использовать. Готовую обработку reset/duplicates нужно реализовать самостоятельно. Публичные примеры не исчерпывают проверяемые случаи; все скрытые варианты остаются в описанном контракте.

## D Проверка и evidence

```bash
./course build
./course test
./course check --mode homework --output evidence/homework-check.json
```

Перед `check` остановите другие launch этого задания. `check` сам выполняет свежий headless запуск и cleanup. Для интерактивного наблюдения используйте `./course homework` и во втором терминале `./course observe --mode homework ...`.

Сохраните:

1. Headless report с доступностью всех сенсоров, движением, pause, steps и reset.
2. Два отчёта при разных target RTF с неизменными rates; объясните sim rate и wall rate по измеренному RTF.
3. Два свежих запуска одинакового сценария с одним seed; сравните motion metrics с допусками.
4. Три стационарных noise profiles `ideal`, `white`, `biased` с gyro mean/std и размером выборки.
5. Собственный тест, обнаруживающий конкретную ошибку. Например, смешение эпох после reset или неверная обработка повторного stamp.

Команды опытов совпадают с практикой с заменой `practice` на `homework`. После reset наблюдайте clock jump и начальную pose, затем полностью перезапустите сцену для следующего прогона. Recovery без перезапуска не требуется.

В `docs/diagnosis.yaml` по [шаблону](diagnosis.template.yaml) кратко укажите наблюдение, причину, изменение, проверку и предел вывода. В evidence фиксируйте команду, seed, target и measured RTF, image/package versions. Скорость компьютера сама по себе не является основанием для снижения оценки.

## Оценивание

| Компонент | Баллы |
|---|---:|

| Движение, сенсоры, bridge, clock и TF | 40 |

| Собственный тест и объяснение | 5 |

Преподаватель выполняет независимую проверку submitted commit. До 85 баллов подтверждаются программными проверками, оставшиеся 15 — просмотром evidence, воспроизводимости, собственного теста и объяснения. Наличие `passed: true` в студенческом отчёте не определяет оценку.

Допустимые варианты: другие namespace/frame prefix/world name, выборки с reset/duplicates, разные seed и ограниченные задержки готовности. Типы, units и опубликованный контракт остаются прежними. Два робота, Nav2, SLAM, `ros2_control` и восстановление без перезапуска в обязательную часть не входят.
